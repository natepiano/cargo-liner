## [Unreleased]

### Added
- Show how far along a compiling invocation is. The reading is cargo's own: while it compiles it draws `Building [========>    ] 149/403: globset, regex-automata`, and those are units of its build plan finished and planned, so nothing is estimated. The reading rules the working-directory heading standing over the command, in the summary and in the command's own cell alike, which costs the table no width. A heading stands over every command started from that directory, so where two of them report at once the table falls back to a `state` column with room for a reading per row. The reading is set at the right of that cell and the bar fills it from the left as a background rather than a run of glyphs, so it passes under the number and a finished build reads `100%` on a solid ground instead of beside one. The cell the fill has reached is still drawn in eighths, which is what keeps the bar moving on every unit rather than once every ninth of the build. Neither appears where nothing on the cell has a capture behind it.
- Capture cargo's output so that progress can be read at all, through a shim cargo-tile installs itself: `cargo-tile install` moves each toolchain's real cargo aside to `cargo-tile-real` and takes its name, running it under a pty and mirroring the output to `/tmp/cargo-tile/run-<timestamp>-<pid>.log`. `cargo-tile status` reports what stands in front of each toolchain and `cargo-tile uninstall` gives cargo its name back. The rows in the grid are found by scanning the process table and so belong to other terminals, and a process's output belongs to the terminal that started it -- which is why reaching it takes standing in front of cargo rather than asking it for anything.
- Answer to `cargo tile` as well as `cargo-tile`. Cargo runs any binary on the path whose name starts with `cargo-` as a subcommand, handing it that subcommand name ahead of every other argument, so the command line drops that word and both spellings take the same arguments. This kept working when argument parsing arrived: before it there was none, and the extra word went unread.
- Report progress for runs with no terminal as well, by asking cargo for a progress bar it would otherwise draw only for a tty. Cargo refuses `always` unless a width comes with it, so the shim sets both.
- Say when a command is blocked on another cargo's lock. Cargo locks the build directory, so a second command against the same target waits instead of failing -- it prints `Blocking waiting for file lock on build directory` once and then nothing at all, which from outside is a pid, a climbing duration and no reading, exactly like a build that has not reached its first unit. The `state` column reads the wait out of the capture and names it, and a blocked row brings that column in even where every reading is on a heading already -- a heading is per directory and a wait is per row. It does not contend for a heading itself, having no reading to put there. Position decides, not presence: cargo counts its downloads before it reaches for the lock and the wait line stays in the log after the lock comes free, so whichever of the two markers came last is what the run is doing.
- Withhold a command's own cell while it has nothing running under it, for the subcommands named in `commands.hidden_when_idle` -- `port` to begin with, the sibling terminal UI in this workspace. A command reached as a cargo subcommand but never finishing is open all day with no reading, no compiler and no duration worth reading, so its cell holds a single row saying no more than the summary's one line for it already does -- a cell no build is getting. The summary line stays: what is held back is the cell alone. It opens the moment the command drives a cargo invocation, with that invocation under it, and closes through the usual fade once the invocation ends. The list is only for commands that outlast their work: anything that finishes on its own leaves the grid by finishing.
- List `commands.hidden_when_idle` in the settings overlay, and write the config file back out at startup when it does not already name every setting. The overlay steps through fixed sets of values and a list of subcommands is not one, so that row reports what the file holds and the file is where it is edited -- which left a setting nothing on screen mentioned and nothing on disk mentioned either, since a `config.toml` written before a setting existed does not carry it. The startup write is skipped when the file already says the same thing, and never runs on a file that failed to parse.

### Changed
- Close a cell by having the grid come together over it, rather than by leaving a hole to trade places with the cell after it, then the one after that, until it reached the end. Every one of those swaps drew the hole travelling one way through the cell travelling the other -- two boxes crossing, in the space the eye was watching one of them close. The cell above the departing one and the cell below it now meet in a single travel, with everything after moving up one place in the same move.
- Fix the pile of lines a close that takes a column with it left behind. Closing a cell re-divides every column, so each column is travelling too, but a cell crossing between columns was drawn in the columns as the grid had them before the step -- its two pieces standing in geometry the rest of the frame had already left, their borders falling through the middle of the cells that had widened past them. Both pieces now ride the columns as they stand partway through the move.
- Keep a cell riding a column that is closing from travelling up or down. A cell crossing between columns is drawn as two pieces, one sliding off the edge of the column it leaves and one rising into the foot of the next -- which is the snake every close makes, and is right for a column that stays. A column that is closing is being pushed off the right edge instead, so the slide drew the cell travelling up through a column that was itself travelling sideways: two motions over the same ground, in the one place the eye was watching a column simply go. The closing column now holds one box that goes with it, and only the piece arriving at the foot of the next column rises.
- Rename the `sub` column to `runs`. It counts the cargo invocations running under a command, but read as an abbreviation of `subcommand` -- a different thing the same table already deals with, since `cargo nextest run` is one.
- Put `command` ahead of `compiler` and `runs` in a command's own cell, so the command line starts in the same column it does in the summary rather than after two narrow columns. The command still absorbs whatever width the fitted columns leave, which now follows the column rather than its position at the end of the row.
- Leave `compiler` and `runs` out of the summary. A row there stands for a whole command, and both columns describe a single invocation -- what is compiling under it at this instant, and how many invocations it is managing. A command's own cell still carries them, and the summary spends the width on the command line.
- Start the working-directory headings and the rows under them one space in from the cell border, rather than two and four. A tile is often narrow enough that the left margin was costing the command column its flags.
- Reject arguments that are not a subcommand. 0.1.0 parsed no command line at all, so anything after the binary name was ignored and the grid opened regardless; `cargo-tile install` now installs and `cargo-tile nonsense` is an error rather than a grid.

### Notes
- Installing the shim is always explicit, never done on startup: it stands in front of every cargo invocation on the machine. It changes nothing about what cargo does, prints, or exits with. Query invocations (`cargo metadata`, `--version`) pass straight through, as do this workspace's own terminal UIs, `cargo tile` and `cargo port` -- capturing one would run it under `script` and copy every redraw into a log for as long as it stayed open -- and a nested cargo -- a build script, or cargo driving cargo -- does not open a second capture. Nesting is settled by ancestry rather than by the flag naming a process that is merely still alive: a captured run that outlives the build that started it leaves that flag pointing at a pid alive for hours, and everything inheriting it would go uncaptured for just as long.
- A `--message-format=json` run is captured like any other. Its caller is usually rust-analyzer, and it compiles and takes the build-directory lock, so a run blocked behind one can only say so if the grid can see it. Only the no-terminal path ever captures it -- the pty path needs all three streams on a tty, which a caller parsing the output never has -- and that path mirrors stderr alone, so the JSON on stdout reaches the caller byte for byte. The cost is a log per check, and an editor issues those on every save.
- The shim publishes itself as `CARGO`. Cargo names the binary it is running there, and the tools that wrap it honour that over the path -- `cargo-clippy` and `cargo-nextest` invoke `$CARGO` rather than looking `cargo` up again. Left alone it named the real binary the shim had exec'd into, so every run those tools started went around the shim, and the value outlived its run in any environment that inherited it. It costs nothing to name the shim instead, since the shim ends in the real binary either way.
- A run already going cannot be captured. A shim is only ever there for the processes it starts, so anything mid-flight when it is installed shows in the grid without a bar until it is run again. Installing while a build runs is otherwise safe: a running cargo holds its binary open, so moving that file aside does not disturb it.
- `rustup update` replaces the shim with a fresh cargo. Running `cargo-tile install` again repairs it, and is safe to repeat: the real binary is only ever moved, never written over, and anything holding the name without the shim's marker in it is treated as the real cargo.
- The shim is POSIX `sh` and runs on macOS and Linux. The two `script` implementations disagree -- the BSD one takes a command and its arguments, util-linux's takes a single command line after `-c` and needs `-e` to exit with the child's status -- so the shim settles which is present before calling it, and falls back to the no-terminal path where there is no `script` at all. Both are told to flush the log on every write, `-t 0` and `-f`: the BSD one defaults to holding output for thirty seconds at a time, which is longer than many runs last and long enough to make a blocked run useless to read -- cargo announces the wait at once and the terminal shows it at once, while the single line it printed sits in a buffer and the grid reads an empty log until well after the lock came free.
- A run that reached no unit and waited on no lock deletes its own log as it ends, having recorded nothing the grid could read -- which is what an editor's check on every save amounts to. The logs that did record something are left behind under `/tmp/cargo-tile/`, and whatever cleans `/tmp` on the system is what bounds the directory -- macOS sweeps files after a few days, many Linux systems clear it at boot. A run counts as live only while its marker under `/tmp/cargo-tile/state/pids/` exists, so the logs can be deleted at any time.
- Without the shim installed nothing breaks -- the `state` column stays out and headings draw no rule.

## [0.1.0] - 2026-08-21

### Added
- Establish cargo-tile as the starting point for a new `tui_pane` application, tagged `app-template-v1`. The crate is a complete TUI with no application in it: framework globals, the settings / keymap / global-shortcuts overlays, live theming, a status line, restart in place, demand-driven rendering, and input on its own thread. See `crates/tui_pane/docs/as-built/app-template.md`.
- Edit key bindings from the keymap overlay: Enter on a row captures the next keypress, checks it against every binding in force, writes `keymap.toml`, and reloads. The `?` overlay hands off to the same editor with the selected row already open.
- Show the cargo invocations running on this machine, one row per invocation, grouped by the working directory they were started from and ordered by path. A process is classified as cargo by its argv rather than its process name, so a wrapper or a renamed binary is still attributed correctly, and a start-time tie between two candidates resolves toward the newer pid.
- Tile the pane into an animated grid of cells, one per running invocation. The layout is a pure function of the cell count, growing by greedy fill up to `initial_rows` squared and then toward the next square. A cell moving between columns is drawn as two placements -- the piece leaving the old column and the piece arriving in the new one -- so it reads as sliding rather than jumping, and transition progress is fixed-point so the animation is deterministic. A command finishing in the middle empties its cell and the grid closes up around it, with focus following its cell.
- Show the running cargo-tile version in the pane title.
- Own theme content in the app rather than the framework: the crate ships its own theme variants, and its grid draws on the shared pane border in the inactive shade regardless of focus.
